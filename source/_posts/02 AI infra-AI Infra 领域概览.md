这篇文章的定位是"地图"而不是"教程"：不推导公式、不贴命令，目标是回答三个问题——**AI Infra 是什么、为什么突然变得重要、它的技术栈大致长什么样**。希望能帮到和我一样想入门这个方向的朋友。

## 一、为什么需要 AI Infra：显存墙与领域版图

### 显存墙：一切故事的起点

大模型和传统深度神经网络在数学上没有差别——都是矩阵乘法加非线性激活。那为什么十年前没人谈"Infra"，今天它却成了最抢手的方向之一？根本原因不在算法，而在硬件。

传统的视觉模型参数量约 100MB，一张消费级显卡甚至一块树莓派就能跑起来。而主流大模型的参数量已经到了 2T 级别，FP16 精度下仅权重文件就有约 **4TB**——比前者高出四个数量级。做个简单的算术：NVIDIA B200 单卡显存约 180GB，一台 8 卡 DGX 服务器的总装载量是：

$$8 \times 180\,\text{GB} = 1.44\,\text{TB} < 4\,\text{TB}$$

连权重都装不下。这还只是推理的下限——训练时除了权重，还需要保存梯度、优化器状态（比如 Adam 为每个参数额外存动量和二阶矩两份数据）和前向传播的激活值，**训练所需显存大约是模型大小的 8 倍**。模型量化（用更低精度表示参数）可以缓解这个问题，但治不了本。

单机装不下，就只剩一条路：把模型拆开，用多机多卡来算。大模型训推从此迈入分布式计算，与高性能计算（HPC）高度合流——早期做 AI Infra 的人才，很多就出身于 HPC 实验室。而多机多卡引入的通信、同步、一致性问题，正是 AI Infra 工程师每天要回答的问题。所以这个领域的核心命题可以概括为一句话：**当模型已经无法由单张 GPU 独立完成计算之后，怎样让成百上千张 GPU 像一台机器一样协同工作？** 它的价值不在于拥有多少 GPU——买卡是谁都能做的事——而在于如何高效地调度它们。

### 领域版图：五大板块与"训推"工种

业界通常把 AI Infra 相关工作分成五大板块：

| 板块 | 干什么 | 代表技术 |
|------|--------|----------|
| 计算集群 | GPU/TPU 节点、通信协议、底层调度 | NCCL、Slurm、Ray |
| 数据与存储（data infra） | 向量数据库、数据集与权重管理、Agent 数据回流 | 随可训练数据枯竭越来越重要 |
| 训练 infra | 让训练代码在千卡万卡集群上正常、高效、稳定地跑 | Megatron-LM、DeepSpeed、ColossalAI |
| 推理 infra | 模型部署上线、高可用高并发、降低推理成本 | vLLM、SGLang |
| Agent Infra | 高性能 sandbox、Agent 评估平台、内部 MCP 服务 | 暂未独立成工种 |

两个值得了解的业界共识。其一是**工种界定**：一般只有做训练和推理的工程师会被叫做"AI Infra 工程师"（简称"训推"）——计算集群交给机架工程师和运维团队，data infra 和 agent infra 只在少数前沿公司被划入 infra 范畴。其二是**"训练后端 / 推理后端"的说法**：Agentic RL（智能体强化学习）兴起后，Megatron、DeepSpeed 这类传统训练框架被称为"训练后端"，推理侧则直接复用现成的推理框架做"推理后端"，比如智谱的 slime 框架默认组合就是 Megatron + SGLang。

## 二、硬件层：从单机互联到万卡集群

要理解后面所有的软件设计，必须先理解底层硬件，因为**上层并行策略的边界，恰恰是下层硬件的边界**。一个训练集群"好不好用"，一半取决于通信性能，这一层的主线就是通信带宽的升级之路。

### 单机之内：为什么是 8 卡，以及 PCIe 的瓶颈

一台大模型训练服务器的逻辑组成和普通 PC 没什么不同：CPU、内存、GPU、PCIe 总线、网卡、本地存储。

![GPU 服务器的基本组成](/my-blog/assets/obsidian/02%20AI%20infra-AI%20Infra%20%E9%A2%86%E5%9F%9F%E6%A6%82%E8%A7%88/gpu-server-structure.webp)

主流形态是**单机 8 卡**，这背后是很实在的工程权衡：8 卡满载功率约 14.5 kW（相当于 10 台吹风机同时开），已逼近单机供电极限；风冷散热的噪音大到进机房要戴隔音耳机；8 是 2 的次幂，方便并行算法切分；卡越多，单卡故障时全机停转排查的损失越大，通信拓扑也越难做对称。单机 16 卡在部分高端云厂商已有库存，是未来的趋势，但目前 8 卡仍是讨论算法时的标准单位。

另一个重要概念是 **NUMA（非一致内存访问）**。单机八卡服务器通常是双路 CPU：每个 CPU 连同同侧的 4 张卡、内存构成一个 NUMA 节点。节点内部的访问是高速且一致的，但跨节点访问要走 CPU 之间的专用互联协议（Intel 叫 UPI，AMD 叫 Infinity Fabric），**延迟更高、有效带宽更低**。这意味着"哪张卡和哪张卡通信"并不是等价的——物理位置决定通信成本。

![NUMA 双路八卡服务器架构](/my-blog/assets/obsidian/02%20AI%20infra-AI%20Infra%20%E9%A2%86%E5%9F%9F%E6%A6%82%E8%A7%88/numa-dual-socket-8gpu.png)

在这个结构里，GPU 之间最原始的通信路径是 **PCIe 直连**：数据要走 CPU 的 Root Complex 中转，如果系统不支持 PCIe P2P，甚至还要借内存做二传手。PCIe 5.0 x16 的理论单向带宽约 63 GB/s，实测 GPU 间有效带宽往往只有 **23–29 GB/s**。改进方案是加一颗 **PCIe Switch**，让同一 NUMA 节点下的 GPU 绕开 CPU 直接横向通信，带宽接近翻倍到 48–58 GB/s。但这个数字依然喂不饱训练——有估算表明，在典型的张量并行配置下，仅 PCIe Switch 的通信时间占比就会达到 40%–60%。一半的电费和卡时花在等数据上，这显然不能接受。

### NVLink 与 NVSwitch：NVIDIA 的破局

PCIe 的带宽极限是由标准代际锁死的，不换代就无法突破。于是 NVIDIA 在 2016 年推出了专用高带宽互联 **NVLink**。以 A100 为例，卡上引出 3 个 NVLink 接口，用 **NVLink Bridge**（一个插在两张卡之间的小桥接器）连接相邻的 GPU，单桥单向带宽 100 GB/s，三个合计 600 GB/s——比 PCIe 高了一个数量级。

但 Bridge 有个看似奇怪的限制：**每张卡只能和唯一一个邻居两两互联**。为什么不能像组网一样随便连？原因是集合通信的高效依赖于**对称拓扑**：如果 GPU0—GPU1、GPU1—GPU2 各用一桥，那么 GPU0 到 GPU2 就要经 GPU1 中转，通信延迟不一致、拓扑不对称，通信算法也没法均匀施行。所以 8 张 A100 用 Bridge 连完之后，其实是 4 对高速"孤岛"，对内的通信走 NVLink，对外的就只能退回 PCIe Switch 甚至跨 NUMA 的长路径。

![A100 通过 NVLink Bridge 两两互联的拓扑](/my-blog/assets/obsidian/02%20AI%20infra-AI%20Infra%20%E9%A2%86%E5%9F%9F%E6%A6%82%E8%A7%88/a100-pcie-nvlink-topology.webp)

终极方案是 **NVSwitch**——一颗专门转发 NVLink 数据的交换芯片。DGX A100 用 6 颗 NVSwitch 把 8 张卡连成**全互联**：每张卡引出 12 条 NVLink 分摊到 6 颗交换芯片上，任意两卡之间都是满带宽直连，拓扑完全对称。这也是为什么支持全互联的高端训练卡（SXM 封装，没有金手指的专用模组）必须配特制底板——NVLink 走线直接做在底板内部，没法在普通主板上"打补丁"。

![DGX A100 的 NVSwitch 全互联结构](/my-blog/assets/obsidian/02%20AI%20infra-AI%20Infra%20%E9%A2%86%E5%9F%9F%E6%A6%82%E8%A7%88/dgx-a100-nvswitch.webp)

### 多机之间：IB、RDMA 与分层组网

NVLink 再快也出不了机箱。跨机器通信时，普通以太网有两个硬伤：一是带宽，传统 100 Gb/s 网口只有约 12.5 GB/s，比 NVLink 慢一个数量级；二是中转开销，网卡在设计上不支持直接读写显存，数据要走"GPU → 内存 → 内核协议栈 → 对端"的长路径，CPU 全程参与搬运，延迟和带宽双输。

解法是 **InfiniBand（IB）网卡 + RDMA**：RDMA（远程直接内存访问）让两台服务器绕过 CPU 和内核协议栈直接交换内存数据，配合 GPUDirect 甚至可以网卡直读写显存。典型的 DGX A100 每台配 8 张 IB 网卡、对应 8 张 GPU，机间形成 8 条独立高速通道。向上扩展的思路是把网络拆成多个**平面**再分层堆交换机（Clos 网络）：直连服务器的交换机叫 Leaf，负责汇聚上行的叫 Spine，更大规模再加 Core 层，逐层把容量从几百卡推到万卡。

![Leaf + Spine 的两层 Clos 组网](/my-blog/assets/obsidian/02%20AI%20infra-AI%20Infra%20%E9%A2%86%E5%9F%9F%E6%A6%82%E8%A7%88/two-tier-clos-leaf-spine.webp)

这里有个值得记住的判断：**"拥有一万张卡"不等于"万卡集群"**——把一万张卡连成一片高速互联的网络，组网成本可能接近再买一万张卡。不想自己组网的终极选项是 NVIDIA 的整机柜方案 NVL72：一个柜子 72 张 GPU、机内全互联、整机液冷，2026 年市价大约 6000–7000 万人民币。顺带一提，2019 年 NVIDIA 花约 70 亿美元收购了 IB 技术的核心厂商 Mellanox——NVIDIA 真正的护城河从来不是单卡算力，而是 CUDA + NCCL + 网络软硬件合在一起的超级生态。

## 三、软件抽象层：通信原语与 NCCL

### 为什么需要一套新的"通信语言"

硬件拓扑讲完了，但写训练代码的人显然不想直接面对 PCIe 和 IB 的走线。**通信原语就是硬件之上的第一层软件抽象**：忘掉具体链路，只保留"GPU 之间通信速率不同"这一个事实。

为什么不用操作系统教科书上那套进程间通信（信号量、消息队列、管道、内存映射）？三个原因：它们操作的是系统内存而不是 GPU 显存；它们没有考虑多机多进程的情形；它们不是为分布式计算设计的，通信模式描述起来复杂，不利于调度规划。于是业界沉淀出一套泛用的通信原语——就像编程语言里的 `if`/`for` 一样基础，却能组合表达全部并行通信需求，而且与硬件无关：纯 CPU 超算、GPU 集群、国产 NPU，顶层都是近乎同一套接口。

![P2P 通信 vs 集合通信](/my-blog/assets/obsidian/02%20AI%20infra-AI%20Infra%20%E9%A2%86%E5%9F%9F%E6%A6%82%E8%A7%88/p2p-vs-collective.webp)

### P2P 通信与集合通信

**P2P（点对点）通信**最简单：数据从一个 rank 流向另一个 rank（rank 就是"进程/GPU 的全局编号"，world_size 是总卡数——分布式编程里每个 GPU 对应一个独立进程，靠这些编号互相识别）。基本操作有 Send / Recv 及其非阻塞版本 iSend / iRecv 四种。要点是**阻塞语义**：Send 和 Recv 必须成对出现，如果 rank0 先到了 Send 而对端还没到 Recv，rank0 就卡在原地；如果对端干脆崩溃或跳过了 Recv，rank0 就**永远卡住**——这是分布式训练里最高频的 bug（hang）的典型成因。

**集合通信（Collective）**解决的是另一类问题：N 张卡要按规律同时执行对称的集体操作，用 P2P 来写既繁琐又负载不均。最经典的例子是数据并行的梯度同步：4 张卡各存一份完整模型副本，一个 batch 平摊到 4 张卡上算，反向传播后各卡的梯度不一样，必须汇总求平均再更新——否则四张卡训练的就不再是同一个模型。

![数据并行：各卡梯度需要汇总同步](/my-blog/assets/obsidian/02%20AI%20infra-AI%20Infra%20%E9%A2%86%E5%9F%9F%E6%A6%82%E8%A7%88/data-parallel-dp.webp)

如果用 P2P 实现：全部发给 rank0 → 算均值 → 再发回去。rank0 承担所有通信和计算，其余卡干等，一个逻辑上完全对称的操作被写成了极不对称的代码。集合通信把这类需求抽象成一行调用：

```python
dist.all_reduce(x, op=dist.ReduceOp.SUM)  # 各卡梯度求和，结果人人有份
```

优雅、对称、高效。常用操作就这么几种：**Broadcast**（一个 rank 广播给所有人）、**Reduce / AllReduce**（归约——把一组数据用满足结合律的运算符合并，加法、乘法、取 max 都是归约；AllReduce 让结果每个 rank 都有一份）、**Scatter / Gather / AllGather**（分片分发与收集）。

![集合通信操作总览](/my-blog/assets/obsidian/02%20AI%20infra-AI%20Infra%20%E9%A2%86%E5%9F%9F%E6%A6%82%E8%A7%88/collective-ops-overview.webp)

两个容易忽略的重点。第一，集合通信只从数学层面规定"一次通信达成什么效果"（输入输出），**不指定怎么传**——具体走什么拓扑、分几步传，是后端的事，这正是它能跨硬件通用的原因。第二，AllReduce 带有 **barrier 语义**：组内所有 rank 都等归约完成才能继续，一个 rank 挂掉，全队卡住。这是它同步正确的保证，也是 hang 问题的另一面。

### NCCL：原语之下的实现

现代 AI 软件很少直接操作硬件 SDK，而是套一层与硬件无关的**通信前端**——PyTorch 的 `torch.distributed` 是事实标准（Megatron-LM、DeepSpeed 都选它），HPC 领域则是经典的 MPI。前端之下，真正干活的**后端**在 NVIDIA GPU 上就是 **NCCL**（NVIDIA Collective Communications Library，开源 C++ 库，对应华为的叫 HCCL）。

NCCL 的工作方式值得了解，因为它解释了很多"玄学"现象。初始化通信组时，NCCL 先做**拓扑发现**：摸清所有 GPU 的连接关系——哪些卡之间有 NVLink、哪些同机、哪些跨机、走哪张网卡，相当于自动构建一张多机版的连接地图。之后每次通信调用并不会立刻发数据，而是先登记进调度队列，再根据三个要素自动选择通信算法：**拓扑信息 + 通信原语类型 + 单卡数据量**。相同规格的选择结果会被缓存，不会每次重算。

算法选型的直觉一句话就够：**大消息走 Ring**——所有卡首尾相连成环，数据切片沿环流动，充分利用每条链路的带宽；**小消息走 Tree**——把 rank 组织成二叉树逐层归约，轮数从与卡数成正比降到对数级，压低延迟；如果集群有 NVSwitch / SHARP 这类支持**在网计算**的硬件，NCCL 还会把部分归约直接 offload 给交换芯片，让交换机顺手把加法做了。平时完全不用手动干预，只有排查性能问题时才需要通过环境变量强制指定算法，配合 `NCCL_DEBUG=INFO` 日志看它实际选了什么、走的是 IB 还是以太网。

## 四、上层应用：并行算法与训推工程难点

### 并行算法：被硬件塑造的切分艺术

原语和 NCCL 再往上，就是并行算法——回答"模型和数据怎么切"的问题。三大经典范式：

| 范式 | 切什么 | 通信特征 |
|------|--------|----------|
| 数据并行（DP） | 切 batch，每卡一份完整模型副本 | 每步一次梯度 AllReduce |
| 流水线并行（PP） | 按层切分（层间），不同的层放不同的卡 | 层间点对点传递激活值，单次量小但频率高 |
| 张量并行（TP） | 切层内的矩阵乘（层内），一层拆到多卡 | 每层都要 AllReduce，单次量大 |

DP 最容易理解，但上限被单卡显存锁死——模型本身必须完整放进一张卡。突破显存墙靠的是后两者。以 Megatron-LM 的张量并行为例，它的切分有个精巧之处：对同一个 MLP 的两个矩阵乘，第一个按列切（各卡独立算完独立过激活函数，零通信），第二个按行切（各卡算部分和，最后做一次 AllReduce 收口），两个矩阵乘融合为一组后，**整层前向只需要一次 AllReduce**。自注意力块同理：Q/K/V 投影按列切、输出投影按行切。框架还用一对共轭的通信算子封装切分点——前向恒等、反向 AllReduce 的算子负责聚合梯度，前向 AllReduce、反向恒等的算子负责聚合激活——一个 transformer 层前向加反向总共只需 4 次 AllReduce，通信开销极小。

Megatron 还有不少省通信的工程巧思，很能体现这个领域的思维方式：**能复制计算就不通信**——dropout、LayerNorm、残差连接这类轻量操作在各卡各留一份副本重复计算，避免"单卡算完再广播"的通信；**Loss 融合**——输出层并行后不把所有卡的 logits 汇总，而是融合交叉熵计算、只聚合一个标量 loss，通信量从和词表大小成正比降到常数级。

三种范式彼此正交，可以自由组合（经典的 "TP × PP × DP" 混合并行）。而组合的方式**被硬件拓扑直接塑造**：TP 每层都要通信、频率太高，所以一般只限制在单机内部，吃 NVLink/NVSwitch 的高带宽，实践中 TP 规模一般不超过单机；跨机通信贵，就交给通信频率低的 PP 和 DP。顺带一提，MoE 模型里的专家并行（EP）和 TP 分工不同——TP 切的是单层通用的矩阵运算，EP 切的是 MoE 的专家网络——两者也可以组合。回到第二章的硬件地图：上层算法画的每一条边界，都能在下层硬件里找到原因。

也要有现实的预期：大规模分布式训练中 GPU 利用率一般到不了 90%，优秀的并行算法让总和平均利用率达到 **40% 以上**就已经很棒了。剩下的时间，都花在等待通信上——这也是为什么前面整整两章都在讲通信。

### 训练 infra：让几千个进程像一个人一样训练

训练 infra 的基本模型是"**一卡一进程**"：主流框架为每张 GPU 启动一个独立进程，进程间内存彼此隔离——原本单机上一块内存里的数据传递，变成了进程间、GPU 间、服务器间三级的通信。真正执行矩阵运算和通信的也不是 Python，而是底层的 C++、CUDA 和 NCCL。

随之而来的是**分布式计算图**问题：每个进程只维护本地计算图，跨设备的依赖要靠额外传递激活值、梯度和参数状态来缝合——所以分布式训练的总显存占用会**大于**模型本身的参数，这不是 bug，是分布式的固有开销。

训练 infra 工程师的日常工作，就是在这样的模型上做三件事：**正确性**（几千个进程的同步语义不出错，梯度不错位）、**效率**（用并行策略和计算-通信重叠把通信开销藏起来，把 GPU 利用率往上拉）、**稳定性**（处理分布式系统的老朋友：hang、慢节点掉队、硬件故障——千卡集群里"每天都有卡坏"不是玩笑）。前面说过，最高频的故障就是 hang，排查时连日志都要带上 `[local_rank/rank]` 标头，才能定位到底是哪台机器的第几个进程卡住了。

### 推理 infra：自回归的诅咒与破局三板斧

推理没有反向传播，看似比训练简单，但它有自己独特的难题，根源是大模型推理的三个特点：**自回归生成**（逐个 token 串行吐出，生成结果要拼回输入再算下一个，单个请求无法并行加速）、**高并发**（模型太大，用户只能用云服务，服务必须扛住并发）、**商业模式约束**（API 按量计费，infra 必须保证不赔本）。

落到具体系统上，传统的推理方式有三个非常符合直觉的痛点：

1. **KV Cache 显存碎片化**：生成每个 token 都要缓存它的 Key/Value 向量，传统做法为每个请求分配一块连续显存。请求来来去去，显存里全是用不上的"空洞"——和早期操作系统的内存碎片问题一模一样；
2. **静态批处理的"陪跑"**：凑齐一批请求一起跑，生成 10 个 token 的请求得陪着生成 500 个的请求跑完才能释放资源，GPU 利用率随请求逐个完成一路下滑；
3. **预分配浪费**：不知道请求最终会生成多长，只能按最大长度预留显存。vLLM 论文的调查显示，碎片和过度预留浪费掉的显存高达 **60%–80%**——花 80GB 显存的钱，只用上十几 GB。

![KV Cache 的显存碎片化问题](/my-blog/assets/obsidian/02%20AI%20infra-AI%20Infra%20%E9%A2%86%E5%9F%9F%E6%A6%82%E8%A7%88/01-kv-cache-fragmentation.png)

vLLM 的破局方式漂亮在它几乎是"操作系统思路的平移"：

- **PagedAttention**：直接借鉴虚拟内存——程序看到连续地址空间，物理页却可以离散存放。vLLM 把每个序列的 KV Cache 切成固定大小的块，物理块在显存中非连续存放，用 Block Table 维护映射。由于所有块大小相同，任何空闲块都能给任何请求用，碎片问题被彻底消除，浪费只剩下每个序列最后一个没填满的块。
- **连续批处理（Continuous Batching）**：打破"等整个 batch 跑完"的模式，每个推理迭代都检查：有没有请求完成（腾出资源）？等待队列里有没有新请求能调度进来？请求随来随走，GPU 始终保持接近满载，"陪跑"不复存在。

还有一个理解推理性能的钥匙：**Prefill 与 Decode 是两个计算特性截然不同的阶段**。Prefill 阶段要一次性处理整个 prompt，注意力涉及 N×N 的矩阵运算，是**计算密集型**，GPU 的 Tensor Core 能跑满；Decode 阶段每次只处理 1 个新 token，计算量小，却要读完整段 KV Cache——以 A100 为例，算力 312 TFLOPS 而显存带宽只有 2 TB/s，瓶颈瞬间从计算转移到访存，是**访存密集型**。这个差异直接指导优化：Prefill 适合靠大 batch 提吞吐，Decode 单请求打不满 GPU，必须靠连续批处理把多个请求的 decode 步骤"打包"在一起执行。近年来流行的 PD 分离（Prefill 和 Decode 部署到不同机器上分别优化）也是这个思路的延伸。

在这之上，还有三板斧进一步压榨性能：**KV Cache 本身**（相邻两步生成的前缀完全相同，缓存历史 K/V 避免重复计算——这是一切推理优化的前提）、**投机采样**（用小模型先草拟多个 token、大模型一次校验，打破逐 token 串行）、**量化与算子融合**（压榨单个 transformer 模块的性能）。工业场景还要同时服务成百上千个用户，在榨干算力和满足业务延迟之间做平衡——这一层被称为"推理中台"。

## 五、这个领域正在走向哪里

从 ICML 2026 的 AI Infra 论文能看出三条清晰的主线。**GPU / Training Systems** 方向：通信正在成为编译器的对象（把计算、通信、同步联合编译，而不是算完再交给通信库），训练算法开始直接适配硬件数据格式（围绕新硬件的低精度格式重新设计量化训练），并行策略与模型结构共同设计——MoE、长上下文、稠密 Transformer 的最佳切法各不相同，不再有万能的并行方案。**LLM Serving** 方向：从单纯追求吞吐，转向围绕 KV Cache、长上下文和异构请求做全局资源调度——上一节讲的 PD 分离正是这条主线的代表。**Agent Infra** 方向：随着 Agent 工作负载兴起，开始认真讨论 Agent 的 workflow 管理、并发调节、状态恢复和安全。

背后的共同信号是：**AI Infra 正在从"把 GPU 跑满"走向系统级的全局执行优化**。单点优化的空间越来越小，跨层协同成为主战场。

回头看这整张地图——从显存墙逼出分布式，到硬件拓扑的带宽竞赛，到通信原语与 NCCL 的层层抽象，再到并行算法和训推框架——AI Infra 的每一层都在回答同一个问题：**如何让一千张卡像一张卡那样工作**。而最好的优化，永远发生在层与层的交界处。
